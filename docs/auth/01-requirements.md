# Auth 产品需求与范围

## 1. 目标

交付项目首个可投入后续业务使用的认证模块，支持邮箱密码登录、邮箱验证码注册、当前用户查询、会话刷新和退出。认证判断始终由 API 完成；前端状态只用于界面呈现。

## 2. 第一版范围

### 必须交付

- 注册：用户名、邮箱、密码、6 位邮箱验证码；验证码有效 300 秒且仅可成功使用一次；注册成功后立即建立登录会话。
- 登录：邮箱和密码；返回公开用户资料并通过 HttpOnly Cookie 建立会话。
- 会话：短期 Access Token、较长期 Refresh Token；服务端保存 Refresh Token 摘要，刷新时轮换，支持撤销。
- 查询当前用户：受保护的 `GET /api/auth/me`。
- 刷新与退出：`POST /api/auth/refresh`、`POST /api/auth/logout`。
- 注册验证码邮件：Nodemailer + QQ 服务商，通过环境变量读取账号和授权码。
- 输入校验、稳定错误码、限流、日志脱敏、CSRF 防护及自动化测试。

### 不在第一版

OAuth/第三方登录、短信、忘记密码、MFA、组织与成员业务流程、复杂 RBAC 及其他业务功能。身份模型预留多租户边界，首版不实现组织/成员功能。

## 3. 用户流程

### 注册

1. 用户填写邮箱并请求验证码。
2. API 规范化邮箱，检查邮箱是否已注册及发送限流，生成安全随机验证码并发邮件。
3. 用户填写用户名、邮箱、密码和验证码提交注册。
4. API 校验 DTO、原子消费验证码、哈希密码，并由数据库唯一约束兜底邮箱唯一性。
5. API 创建用户及会话，设置双 Cookie，响应中只返回用户公开资料。

### 登录与恢复

1. 用户提交邮箱和密码。邮箱未注册和密码错误使用稳定错误码区分，按产品要求提示。
2. 前端启动时调用 `/api/auth/me` 恢复用户状态。
3. 当请求因 Access Token 过期返回 `ACCESS_TOKEN_EXPIRED` 时，前端合并并发刷新请求，刷新成功后原请求最多重试一次；非法/撤销凭证返回 `UNAUTHENTICATED` 并直接要求登录。
4. 刷新失败时清除前端用户状态并引导登录。

### 退出

API 必须先撤销服务端当前会话，再清除 Cookie 并报告成功；旧 Refresh Token 即使被再次提交也不得刷新。前端清理当前用户状态及用户相关缓存。Access Token 在默认设计中最长自然存活 15 分钟。

## 4. 字段与验证基线

- 邮箱：去除首尾空白，按统一策略转小写后保存和查找；数据库唯一索引为最终约束。
- 用户名：必填，建议长度 1–80 个 Unicode 字符；具体展示字符规则待产品确认。
- 密码：必填，建议最少 12、最多 128 个字符；不强制大小写/数字组合，限制最大长度以控制计算成本。密码按 Argon2id 哈希，禁止明文存储。
- 验证码：严格 6 位数字，密码学安全随机源；Redis TTL 严格 300 秒，注册用途限定，单次消费。

以上长度及规范化规则将落实为前后端一致的契约；如需调整，请在审核时提出。

## 5. 验收结果

- 合法注册/登录返回公开用户资料并建立 Cookie 会话；任何响应、日志或持久化数据均不包含原始 Token、明文密码或验证码。
- 未认证或无效会话不能访问受保护 API；被停用或删除的用户不能继续通过认证。
- 注册验证码过期、重复消费、错误次数超限以及发送限流均由后端可靠拒绝。
- 邮件发送失败不会把接口报告为发送成功，也不会遗留可被误认为已发出的有效验证码。
- 刷新轮换旧 Refresh Token；同一旧 token 的并发/重放采用安全优先撤销策略，可能要求重新登录；退出撤销服务端会话并清除浏览器凭证。
- 用户身份与未来组织/成员授权分层，组织成员关系由服务端验证，首版不假设用户必属一个组织。
- 前端对邮箱未注册、密码错误、验证码错误/过期、限流及通用故障提供对应反馈。
- 评审通过后按 [验收清单](./06-configuration-delivery.md) 执行实现和验证。
