# 系统架构与安全设计

## 1. 组件边界

| 层                   | 责任                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------- |
| Next.js Web          | 表单和客户端校验、调用 API、显示用户状态、单飞刷新及一次重试；不存储 Token、不决定 API 授权。 |
| NestJS API           | DTO 校验、邮箱规范化、密码验证、验证码与限流、JWT 签发/验证/撤销、Cookie/CSRF、安全错误响应。 |
| PostgreSQL / Drizzle | 用户、已验证邮箱时间、Refresh 会话摘要和轮换/撤销状态；唯一索引保证并发注册正确性。           |
| Redis                | 验证码、冷却/频率限制、错误尝试计数以及短期原子状态；认证依赖 Redis 时失败关闭。              |
| Nodemailer / QQ SMTP | 发送注册验证码邮件；从配置读取 QQ 邮箱账号与 SMTP 授权码，不把凭证写入源码。                  |

## 2. 推荐模块边界

后端在 `apps/api/src/auth/` 下组织 Auth 模块，内部按职责拆分 DTO、Controller、认证编排 Service、密码哈希、邮件发送、验证码/限流、会话存储、JWT Guard 与当前用户装饰器。按需新增 Redis 模块及数据库 Schema。避免为单个调用增加无职责的包装层。

前端在 `apps/web` 内增加认证路由与组件，并建立统一 API 请求入口及当前用户查询能力。错误码和公开用户/API 类型放在共享包，避免前后端重复定义。

## 3. 会话与 Token

- Access Token：建议 15 分钟；只用于 API 认证，声明至少含 `sub`、`iat`、`exp`、`iss`、`aud` 和明确的 token type。校验签名、类型、发行方、受众及期限。
- Refresh Token：建议 7 天，具有独立签名密钥及类型；数据库只保存其不可逆摘要。刷新必须验证会话并原子替换摘要，旧 Token 不可再次刷新。
- 会话附带绝对有效期和最近活动时间；建议绝对期限 30 天，空闲期限 7 天（需审核）。不能靠不断刷新无限延长会话。
- 重放策略：发现旧 Refresh Token 重放，撤销该会话（token family）并要求重新登录。每次轮换通过数据库事务/条件更新保证至多一个成功者。
- 并发刷新与重放：同一个旧 Refresh Token 被并发携带时，服务端无法可靠判断第二次请求是合法并发还是窃取后的重放，不能同时保证旧 Token 重用一律撤销和合法并发不误杀。首版选择安全优先策略：前端单飞合并；后端原子轮换，只有一个请求成功，任何已轮换 Token 再次出现都撤销该会话并要求重新登录。合法并发的败方也会触发撤销。跨标签页使用 Web Locks（可用时）协调刷新并以 BroadcastChannel 通知结果；不默认接受旧凭证窗口。若更重视并发可用性，可另行评审有界幂等窗口及其重放风险。
- 登录/注册为每个设备或浏览器创建独立会话；退出只撤销当前会话。

## 4. Cookie 与 CSRF

Access、Refresh Token 仅通过 HttpOnly Cookie 传输，不出现在 JSON、Web Storage、URL 或日志中。Cookie 的 `secure` 在生产为 true，配置合适的 `sameSite`、Path、Max-Age；不设置宽泛 Domain。若同站部署，优先同源反向代理并使用 `SameSite=Lax`；跨站部署时通常需要 `SameSite=None; Secure`，并需额外评估浏览器第三方 Cookie 限制。

Cookie 认证须有 CSRF 防护，CORS 本身不构成防护。建议对有副作用的方法校验精确 Origin（必要时 Referer）并配合 CSRF Token/自定义请求头；不得只依赖 SameSite。API CORS 必须限制为配置的 Web Origin 并允许 credentials，禁止 `*` 与 credentials 并用。

推荐收紧 Cookie Path：Access Cookie 为 `/api`；Refresh Cookie 仅用于 `/api/auth/refresh`（或兼容清除时一致的受限路径）。设置与 Token 生命周期相符的有效期。若采用 `__Host-` 前缀，Cookie 必须 Secure、Path `/` 且不含 Domain，因此与最小 Path 目标冲突；首版建议不使用该前缀。

## 5. 邮箱验证码与跨存储一致性

验证码由安全随机源生成，Redis 仅保存验证码摘要或采用限制 Redis 访问权限的受控存储，TTL 固定 300 秒。按规范化邮箱构造 key，使用 Lua/原子命令实现冷却、尝试计数与“校验并消费”。建议发送冷却 60 秒、每邮箱每小时最多 5 次、每 IP 每小时最多 20 次；验证码错误最多 5 次后失效（参数化配置，具体值待审核）。

邮件发送流程先占用一个有短 TTL 的发送锁/限流名额，再发信；失败时按原子方式删除临时验证码并释放或保留适当冷却名额，避免攻击者利用失败重置限流。只有发送成功才把验证码作为可验证状态发布。需实现 Lua 或等效可靠流程，不能假设 Redis 与 PostgreSQL 存在跨库事务。

注册时先原子消费验证码，再插入数据库。若数据库失败，验证码保持已消费，用户可重新获取验证码；这是明确的失败关闭恢复策略，可避免并发复用。唯一约束冲突映射为稳定业务错误 `EMAIL_ALREADY_REGISTERED`。消费验证码不是数据库事务的一部分，不做会导致凭证重用的“失败自动恢复”。

## 6. 错误、日志与滥用防护

- DTO 错误统一映射稳定错误码；不向客户端返回 SQL、Redis、邮件服务异常详情或堆栈。
- 邮箱未注册/密码错误按用户交互需求区分；这会产生邮箱枚举面。使用统一响应结构、相近处理时间、登录限流和监控，且不得把敏感内部信息加入响应。产品若优先防枚举，应改为统一凭证错误文案。
- 注册验证码发送、登录、注册、刷新均限流；按 IP 与目标邮箱/账号组合控制，避免仅信任客户端 IP 头。
- 日志记录请求 ID、操作结果、会话 ID 摘要和安全事件，不记录密码、验证码、Cookie、Token、邮件授权码或完整认证头。
- 邮件/Redis/数据库异常应尽早失败，由统一异常层转换为安全错误；不得以绕过验证码/限流作为降级方案。

## 7. 退出与立即撤销的取舍

退出必须在服务端撤销当前会话，使该会话的 Refresh Token 即使仍被持有也无法再刷新；仅清除浏览器 Cookie 不构成登出。撤销操作必须先成功提交，再返回成功并清除 Cookie；撤销失败不能报告登出成功。登出后再次提交旧 Refresh Token 必须被拒绝。无状态 Access Token 在失效前仍可用，默认最长 15 分钟；首版约定 Refresh 会话立即撤销、Access Token 最长自然存活 15 分钟。

## 8. 多租户身份预留

系统身份与租户成员关系分开建模：`users` 表示全局登录身份；未来的 `orgs` 表示组织；`members` 表示 `user_id` 与 `org_id` 的成员关系及组织内状态/角色。认证成功只证明用户身份，不代表其属于当前组织或具有组织权限。首版不创建 org/member 表，也不把单一 `org_id` 固定写入用户记录。

API 应允许未来引入组织上下文、成员查询及基于成员关系的授权。Access Token 首版只承载全局身份和标准声明，不承载长期可信的组织角色快照；租户授权以服务端当前成员关系为准。未来共享数据表按 `org_id` 隔离，并在查询/约束中验证组织边界。注册用户没有默认组织，是否自动创建组织属于未来流程。
