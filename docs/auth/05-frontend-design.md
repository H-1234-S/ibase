# 前端实现设计

## 1. 当前实现基础

`apps/web` 是 Next.js 16 App Router + React 19 起始应用。未发现表单、请求客户端、客户端缓存或认证状态管理依赖。共享 UI 包已有 shadcn 风格 Button/Card。第一版先使用现有 React/Next 能力和 UI 包；只有确认需求无法由现有能力满足时才增加表单/校验库。

## 2. 页面与组件

- `/login`：邮箱、密码、提交状态、字段错误、未注册提示和注册入口。
- `/register`：用户名、邮箱、密码、验证码、发送按钮/倒计时、字段校验和提交反馈。
- 页面级表单负责交互；可复用的 Auth API 方法与错误码解析放在 `apps/web` 内统一模块。
- 使用共享 UI 组件保持项目视觉规范；不得在页面复制认证业务请求逻辑。

具体路由应与后续业务页面布局协调；仓库目前没有路由约定以外的认证页面。

## 3. API 客户端和自动刷新

建立统一 fetch 封装：同源 API 请求携带 `credentials: 'include'`；若 API 使用独立源，也必须携带 credentials 并匹配服务端 CORS/Cookie 配置。对有副作用请求附带 CSRF Token/自定义头。

仅当受保护业务请求收到 `ACCESS_TOKEN_EXPIRED` 时才触发一次刷新；缺失、非法、撤销凭证统一为 `UNAUTHENTICATED`，直接清除状态并要求登录。采用模块级单飞 Promise 合并同一运行环境内并发刷新；刷新成功后将原请求最多重试一次。Refresh 请求不得走自动刷新拦截路径，任何刷新 401 都是终止结果。网络错误、403、其他业务 401 和 5xx 不自动刷新。刷新失败时清除用户查询缓存/状态并通知登录流程。

多个标签页的会话变化通过 `BroadcastChannel` 通知“登录态已变化”，消息不包含凭证。Refresh Cookie 是共享的，因此单飞 Promise 只够协调单个 JS 环境；支持的浏览器使用 Web Locks 对跨标签刷新加锁并广播结果。无法协调的环境仍可能发生竞争，按服务端重放撤销策略要求重新登录，不宣称可无误地区分合法并发与攻击重放。

## 4. 登录态与路由保护

当前用户数据以 `/api/auth/me` 响应为唯一可信来源。页面刷新后重新查询；不得将 `isLoggedIn` 或用户 ID 作为 API 授权依据，也不得把 Token 存入 localStorage/sessionStorage。当前仓库没有缓存库，首版可使用 React context/服务端数据获取中的一种轻量方式；实施前检查 Next.js 边界，避免在 Server Component 中无意暴露/复制 Cookie。

登录/注册成功后使 `/me` 数据失效并重新获取，再按路由策略跳转。受保护页面的客户端跳转仅改善体验，API Guard 必须独立拒绝未认证请求。

## 5. 字段反馈与错误映射

- `EMAIL_NOT_REGISTERED`：清楚提示“该邮箱尚未注册”，提供注册入口。
- `INVALID_PASSWORD`：在密码字段下方显示“密码不正确”。
- `EMAIL_ALREADY_REGISTERED`：提示邮箱已注册并提供登录入口。
- `INVALID_OR_EXPIRED_CODE`：提示验证码错误/过期并允许重新申请（服从发送冷却）。
- `RATE_LIMITED`：显示可读冷却时间，不立即自动重试。
- `VALIDATION_ERROR`：按字段 errors 展示。
- 网络/服务器错误：使用统一通用提示，避免向用户展示内部异常。

前端校验与后端共享字段规则，但后端结果始终为准。验证码倒计时是界面提示，不作为真实限流状态；以 API 的 `retryAfter` 为准。

为多租户预留的客户端状态应区分全局 `User` 与后续选中的组织上下文/`Member`。前端选中的组织仅用于构造请求和导航，不构成成员资格或授权证明；组织页面数据必须由 API 按当前用户成员关系授权后返回。首版不伪造默认组织或角色。
