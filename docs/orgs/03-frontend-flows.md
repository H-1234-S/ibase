# 03 前端页面与用户流程

## 1. 实现约束

- 使用现有 Next.js App Router、React、AuthProvider、`authRequest`、共享类型和 `@ibase/ui`。
- 沿用 shadcn 风格；缺少的 Dialog、Table、Select 等在 `@ibase/ui` 按需补齐。
- 一般操作反馈使用现有右下角 sonner toast；字段错误就近显示，页面级邀请异常提供明确下一步。
- 组织按钮隐藏只是体验优化，服务端授权才是安全边界。
- 现有 `src/proxy.ts`、登录和注册成功跳转必须按本 PRD 调整，不能继续一律跳 `/dashboard`。

## 2. 路由规划

| 路由                        | 访问条件     | 内容                                                          |
| --------------------------- | ------------ | ------------------------------------------------------------- |
| `/onboarding/organization`  | 已登录       | 创建组织；无有效邀请时的初始化入口                            |
| `/orgs/[orgId]/dashboard`   | 本组织成员   | 组织概览、成员数、当前角色、管理入口                          |
| `/orgs/[orgId]/members`     | 本组织成员   | 成员列表；admin 可见角色修改和移除                            |
| `/orgs/[orgId]/invitations` | admin        | 邀请创建、状态列表、重发、撤销、过期重邀                      |
| `/orgs/[orgId]/settings`    | admin        | 危险操作与删除组织                                            |
| `/invitations/[token]`      | 公开但限流   | 邀请预览、登录/注册引导、邮箱匹配与接受                       |
| `/login`、`/register`       | 现有页面扩展 | 保留并恢复邀请上下文                                          |
| `/dashboard`                | 已登录       | 兼容入口，按有效邀请/组织上下文重定向，不再作为唯一 Dashboard |

邀请令牌只用于邀请路由及受控的 Auth 恢复链接，不允许将任意 `next` 外部 URL 当作跳转目标。

## 3. 页面与组件

### 3.1 组织布局

- 顶栏显示当前组织名称、当前用户角色和组织切换入口。
- 切换器列出 API 返回的本人组织；选择后导航到目标组织 Dashboard。
- 组织不存在、已删除或非成员时展示无权限状态，不闪现成员或邀请数据。
- OrganizationProvider 可保存显示上下文，但数据来源必须是对应组织 API。

### 3.2 创建组织页

- 单个名称输入框与创建按钮，提示长度和必填规则。
- 客户端 trim 和基本校验；最终以服务端校验为准。
- 提交中禁用按钮，成功 toast 后进入 `/orgs/[orgId]/dashboard`。
- 名称校验失败显示字段错误；网络/服务器错误允许重试，不伪造成功组织。
- 已选择邀请流程的用户不能被此页截断邀请恢复。

### 3.3 组织 Dashboard

至少显示：组织名称、组织 ID（可复制）、当前成员数、当前用户角色、最近成员摘要和邀请/成员管理入口。

- 加载：骨架或明确加载状态。
- 空状态：无成员摘要时引导 admin 邀请。
- 失败：显示重试，不以旧缓存冒充最新数据。
- member 不显示管理操作；直接访问管理路由时由服务端数据决定无权限页面。

### 3.4 成员列表

列：显示名、邮箱、角色、加入时间、admin 操作。

- 角色修改使用 Select 或弹窗，变更前显示目标成员及新角色。
- 移除成员使用确认 Dialog，明确“只移出组织，不删除账号及其其他组织数据”。
- 自己降级/移除时提示可能失去管理权限或组织访问权。
- 最后 admin 的受限操作由服务端拒绝并给出明确 toast；前端可根据当前数据提前禁用，但不能替代校验。
- 操作成功后重新获取成员和当前角色；若自身已非 admin，立即移除管理入口。

### 3.5 邀请管理

- 创建表单只包含邮箱，不提供 role 参数或 admin 选项。
- 状态筛选：pending、accepted、revoked、expired；默认 pending。
- pending：可重发、撤销；重发遵循冷却和限流。
- accepted：只读，展示接受时间。
- revoked：只读，可重新创建新邀请。
- expired：可重新邀请，生成新令牌和新有效期。
- 列表不得展示原始令牌或 tokenHash；创建成功只提示邮件已发送，不在界面展示邀请 token。

### 3.6 删除组织

- 使用独立危险区域及二次确认 Dialog。
- 文案列出当前实际删除范围：组织、Membership、邀请；当前没有 Project 或外部资源清理能力。
- 要求输入完整组织名称确认；名称不匹配不可提交。
- 成功后 toast，并跳转其他有效组织或创建组织页。
- 失败保留当前页面和重试入口；不得在未确认服务端成功时清空全部组织状态。

## 4. 邀请接受页面

### 4.1 加载与预览

1. 从动态路由取得 token，通过公开预览接口校验。
2. 展示组织名称、被邀请邮箱、角色 member、有效期及邀请状态。
3. 页面及 Auth 恢复页禁止第三方分析脚本；日志、错误上报和 toast 不记录 token。
4. 接受完成或进入终态后用内部路由替换历史记录，清理地址栏敏感参数；不得把 token 写入 localStorage/sessionStorage。

### 4.2 已登录且邮箱匹配

显示“以当前账号加入”，提交接受接口；成功后进入目标组织 Dashboard。若已是成员，按幂等成功处理，不创建重复关系。

### 4.3 已登录但邮箱不匹配

禁止接受，显示目标邮箱与当前账号的差异，提供“退出并切换账号”。不得允许用户仅修改表单邮箱绕过匹配。

### 4.4 未登录但目标邮箱已注册

引导登录，保留受控邀请恢复路径；登录成功后重新查询邀请并再次验证状态、有效期和邮箱匹配。

### 4.5 目标邮箱未注册

引导到现有注册页，可预填邮箱但保持可验证流程：

1. 使用 Auth 发送验证码接口验证同一目标邮箱。
2. 完成注册并建立会话。
3. 返回邀请接受流程，重新校验邀请。
4. 成功后直接进入被邀请组织，不显示强制创建组织步骤。

### 4.6 异常状态

| 状态          | 页面反馈与入口                                         |
| ------------- | ------------------------------------------------------ |
| 无效/不存在   | 通用无效提示，返回首页或登录，不泄露内部信息           |
| 已过期        | 说明已过期，提示联系 admin 重新邀请                    |
| 已撤销        | 说明邀请已失效，提示联系 admin                         |
| 已接受        | 若当前用户已是成员可进入组织，否则提示邀请已使用       |
| 注册中失效    | 注册可保留有效，但明确邀请无法加入，提供正常工作流入口 |
| 邮件/网络失败 | 通用错误及重试，不暴露 SMTP 或数据库细节               |

## 5. 状态恢复与跨标签页

- AuthProvider 仍是全局用户唯一可信来源；新增组织状态不得复制为另一套用户状态。
- 登录/注册后刷新用户与组织列表，再按邀请上下文决定路由。
- 退出登录清空组织上下文；Auth BroadcastChannel 触发时同步刷新或清空组织数据。
- 标签页中的成员被移除或组织被删除后，下一次 API 失败应清理对应上下文，不继续展示可操作的旧页面。

## 6. 表单与错误约定

- 沿用 `ApiSuccess<T>`、`ApiRequestError` 和 `getApiErrorMessage` 的扩展方式。
- 401 统一进入登录恢复；403 显示权限不足；非成员访问组织可按 404 显示“不存在或无权访问”。
- `RATE_LIMITED` 展示服务端返回的等待信息，不自动连续重试。
- `VALIDATION_ERROR` 映射到 name、email 等字段。
- 所有管理按钮处理 busy、成功、失败和重复点击；任何乐观更新都必须能在失败时回滚，首版优先提交后重新查询。
