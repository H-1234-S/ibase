# 05 邀请、邮件与 Auth 恢复流程

## 1. 邀请原则

- 邀请代表“指定组织邀请指定邮箱以 member 身份加入”，不是通用登录凭证。
- 邀请链接本身不证明访问者拥有目标邮箱；邮箱归属由现有 Auth 注册邮箱验证码及登录会话证明。
- 原始 token 只出现在邮件链接和受控邀请流程中，数据库只保存安全摘要。
- 所有状态、过期和接受判断以服务端时间为准。

## 2. 状态机

```text
创建并投递成功 → pending
pending → accepted（唯一一次有效状态迁移）
pending → revoked（admin 撤销）
pending → expired（到期动态判定，读取/重邀时同步规范化）
expired/revoked → 新建一条 pending（新 token，不复活旧 token）
accepted → 终态
```

### 状态与允许操作

| 状态             | 预览       | 接受           | 重发 | 撤销            | 重新邀请                           |
| ---------------- | ---------- | -------------- | ---- | --------------- | ---------------------------------- |
| pending 且未过期 | 允许       | 允许           | 允许 | 允许            | 不新建，提示已有邀请               |
| accepted         | 显示已接受 | 不再产生副作用 | 禁止 | 禁止            | 如仍非成员可新邀请，但通常已是成员 |
| revoked          | 显示已撤销 | 禁止           | 禁止 | 幂等拒绝/无操作 | 允许新建                           |
| expired          | 显示已过期 | 禁止           | 禁止 | 无需撤销        | 允许新建                           |

“重新邀请”创建新记录、新 token 和新的 7 天有效期；不能简单把旧 token 的过期时间延长。

## 3. 创建邀请

1. 校验当前用户为目标组织 admin。
2. 规范化并验证邮箱。
3. 检查该邮箱是否已是组织成员，是则返回 `ALREADY_ORGANIZATION_MEMBER`。
4. 事务内规范化过期记录并检查有效 pending；存在则返回 `INVITATION_ALREADY_PENDING`，由用户选择重发。
5. 生成至少 256 位密码学随机 token，使用 base64url 等 URL 安全编码。
6. 使用带密钥的 HMAC-SHA256 等安全摘要计算 tokenHash；数据库不保存明文。
7. 保存 organizationId、email、固定 role=member、invitedBy、tokenHash、pending、createdAt/expiresAt（7 天）。
8. 提交数据库记录后，使用现有 `WEB_ORIGIN` 构造 `/invitations/[token]` 链接并发送邮件。

邀请邮件至少包含组织名称、邀请者显示名、被邀请角色、7 天有效提示、接受链接及“非本人预期请忽略”。不得附加 tokenHash 或内部 ID 作为授权参数。

## 4. 邮件失败一致性

### 4.1 首次邀请

- 数据库先创建 pending，邮件在事务外发送，避免长时间 SMTP 占用数据库事务。
- 首次发送失败时补偿删除本次尚未投递的邀请，返回 `INVITATION_EMAIL_SEND_FAILED`，不留下用户无法使用的 pending。
- 若补偿失败，记录 requestId 和组织/邀请 ID 供排查；不得向客户端虚假返回成功。
- 由于 SMTP 结果存在不确定性，链接即使偶发投递也不作为授权绕过：若邀请已被补偿删除，接受会失败，admin 可重新邀请。

### 4.2 重发

- 仅 pending 且未过期的邀请可重发。
- 重发沿用当前有效 token 和原过期时间，发送失败时保留原 pending，旧链接仍可使用，admin 可稍后重试。
- 重发受冷却、邮箱/组织/IP 限流；不通过重发无限延长有效期。

该策略明确区分“首次创建失败补偿”和“已有邀请重发失败”，不承诺数据库与 SMTP 的分布式原子性。

## 5. 撤销、过期与重复邀请

- 撤销只接受本组织 pending 邀请，使用条件更新设置 revoked 与 revokedAt。
- 到期后任何接受都失败，即使数据库尚未被定时任务更新为 expired。
- 读取列表时可按 `pending && expiresAt <= now` 展示 expired；创建/重邀事务中同步更新存储状态。
- `(organizationId, email)` 对 pending 建部分唯一索引；过期重邀先在同一事务中规范化旧记录，再插入新记录。
- 同组织同邮箱已有有效 pending 时不重复创建，避免多封相互冲突的有效邀请。

## 6. 邀请预览与令牌安全

- 预览通过 tokenHash 查找记录，按服务端时间重新计算有效状态。
- 对无效 token 返回通用不存在，不说明是摘要错误、组织不存在还是用户不存在。
- token 不进入应用日志、错误上报、分析事件、Referer 目标或第三方脚本。
- 邀请和 Auth 页面不加载第三方分析服务；外跳链接配置合理 Referrer-Policy。
- 接受或终态处理后使用内部路由替换清理地址栏；不将 token 持久化到 Web Storage。
- tokenHash 永不通过 API 返回；邀请管理列表也不提供“复制原始链接”，因为服务端无法恢复明文。

## 7. 已注册用户接受

1. 预览确认 pending、未过期、未撤销、未接受。
2. 未登录时进入登录页，保留仅指向本站邀请流程的恢复路径。
3. 登录成功后重新预览和校验，不能沿用登录前结论。
4. 当前用户必须完成 Auth 邮箱验证，规范化邮箱与邀请目标一致。
5. 邮箱不匹配返回 `INVITATION_EMAIL_MISMATCH`，提供切换账号，不自动加入。
6. 事务内锁定邀请并再次校验，创建 Membership（冲突时不重复插入），再标记 accepted/acceptedAt。
7. 已是本组织成员时按幂等成功处理；不得创建第二条 Membership。
8. 成功后进入被邀请组织 Dashboard。

## 8. 未注册用户接受与 Auth 复用

1. 邀请预览只用于引导，不视为邮箱已验证。
2. 进入现有 `/register`，可预填目标邮箱；保留邀请恢复上下文。
3. 调用现有 `/api/auth/email/send-code`，向目标邮箱发送 6 位验证码，沿用冷却、限流和一次性消费。
4. 调用现有 `/api/auth/register` 创建 `emailVerifiedAt` 有效的用户并建立会话。
5. 注册完成后回到邀请接受，重新校验邀请状态、过期、撤销及邮箱匹配。
6. 接受成功直接进入被邀请组织；不强制创建自己的组织。
7. 若邀请在注册中失效，明确提示邀请无法使用，同时保留正常创建组织/登录工作流。

普通注册没有邀请上下文时才进入创建组织初始化；两种后续路由必须由“邀请上下文 + 实际邀请状态 + Membership”共同决定。

## 9. 原子接受与重放语义

推荐事务顺序：锁定邀请行 → 校验 pending/expiresAt → 校验当前用户邮箱 → 插入 Membership 或处理唯一冲突 → 条件更新 accepted → 写审计 → 提交。

- 两个并发请求最多一个执行状态迁移和新增关系。
- 同一用户的重复请求可幂等返回已有成员结果，但不重复写审计或发送成功邮件。
- 不同用户即使拿到已接受 token，也不能复用加入。
- tokenHash 唯一约束防止摘要碰撞导致跨邀请匹配。

## 10. 配置与本地验证

复用：`EMAIL_USER`、`EMAIL_PASSWORD`（QQ SMTP 授权码）、`EMAIL_FROM`、`WEB_ORIGIN`、Redis 和 Auth 注册验证码接口。

新增或明确：`INVITATION_TOKEN_SECRET`（独立于 Auth 验证码派生用途）、`INVITATION_TTL_HOURS=168`、邀请限流配置。生产使用独立高熵密钥，不提交真实凭证。

本地联调应使用可控 SMTP 或邮件捕获工具，并分别模拟：发送成功、首次发送失败、重发失败、超时和限流。自动化测试使用邮件服务替身，不依赖真实 QQ 邮箱。
