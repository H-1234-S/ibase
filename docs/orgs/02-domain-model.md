# 02 领域模型与业务规则

## 1. 领域关系

```text
User 1 ── N Membership N ── 1 Organization 1 ── N Project（未来模型）
                              │
                              └── N OrganizationInvitation

Organization 1 ── N OrganizationAuditLog（最小审计记录）
```

- User 是全局身份，不属于任何单一组织。
- Organization 是项目和组织资源的归属边界。
- Membership 是 User 与 Organization 的多对多关系及角色载体。
- Invitation 是某一组织向规范化邮箱发出的单次加入凭证。
- Project 必须直接属于 Organization；当前仓库尚无 Project 模型，本版不虚构项目实现。

## 2. Organization

### 2.1 字段语义

- 主键使用 UUID，作为路由和 API 的稳定标识。
- `name` 为显示名称，不要求全局唯一。
- `createdBy` 是创建者审计字段，不是 owner，也不提供额外永久权限。
- `createdAt`、`updatedAt` 使用服务端时间。

### 2.2 名称规则

1. 服务端去除首尾空白后校验。
2. 规范化后长度为 1–80 个字符。
3. 必须包含至少一个非空白字符，不允许控制字符。
4. 允许中文、字母、数字、空格及常见名称标点；不做全局唯一限制。
5. 第一版不引入 slug；如未来增加 slug，必须与显示名称分离并单独保证唯一性。

### 2.3 创建规则

- 只有已认证且完成 Auth 邮箱验证的用户可以创建。
- Organization 与创建者 admin Membership 必须同事务写入。
- 创建成功后新组织成为当前组织上下文；失败不得留下只有组织或只有成员关系的半状态。
- 已有所属组织的用户也可继续创建组织。

## 3. Membership

### 3.1 基本规则

- `(organizationId, userId)` 唯一；用户在同一组织只有一条有效关系。
- 用户可属于多个组织，同一用户在不同组织可有不同角色。
- 角色只存于 Membership，不写入全局 User。
- `createdAt` 表示加入时间；角色更新只改变 `updatedAt`，不重置加入时间。
- 接受邀请与重复接受通过唯一约束和事务保证幂等。

### 3.2 移除规则

- admin 可移除本组织其他成员，也可按相同规则移除自己。
- 只能删除目标组织内的 Membership，不得删除 User、Auth Session 或其他组织 Membership。
- 被移除用户的全局登录态可以继续存在，但其后续目标组织 API 请求必须立即失败。
- 与成员相关的邀请历史保留用于状态展示和审计，不因移除成员而盲目删除。
- 最后一位 admin 不能被移除，包括移除自己。

## 4. 角色与权限

### 4.1 角色定义

- `admin`：组织管理员，可执行全部组织管理操作。
- `member`：普通成员，只读组织与成员信息，并根据未来项目级权限访问项目。

### 4.2 权限矩阵

| 操作                 | admin                   | member         | 非成员 |
| -------------------- | ----------------------- | -------------- | ------ |
| 查看组织详情         | 允许                    | 允许           | 拒绝   |
| 查看成员列表         | 允许                    | 允许           | 拒绝   |
| 查看本人所属组织列表 | 允许                    | 允许           | 不适用 |
| 邀请成员             | 允许                    | 禁止           | 拒绝   |
| 查看/撤销/重发邀请   | 允许                    | 禁止           | 拒绝   |
| 修改成员角色         | 允许                    | 禁止           | 拒绝   |
| 移除成员             | 允许，受最后 admin 保护 | 禁止           | 拒绝   |
| 删除组织             | 允许                    | 禁止           | 拒绝   |
| 访问项目             | 仍需项目级授权          | 仍需项目级授权 | 拒绝   |

### 4.3 角色变更规则

1. admin 可以将本组织成员提升为 admin 或降为 member。
2. 不允许通过客户端伪造 userId、organizationId、membershipId 或 role 修改其他组织成员。
3. admin 数量必须始终大于等于 1。
4. 自己降级允许，但前提是操作后仍有至少一名其他 admin。
5. 并发降级、移除或角色变更必须在同一事务内锁定组织并重新计算 admin 数量。
6. 角色不放入长期 Access Token；每次组织请求读取数据库，使变更立即生效。
7. 邀请不接受客户端传入 role，邀请初始角色固定 member；后续升 admin 走上述流程。

## 5. 最后 admin 不变量

以下操作必须在提交前验证操作后的 admin 数量：

- admin → member 降级。
- 移除 admin，包括移除自己。
- 接受邀请或其他未来 Membership 变更不得意外减少 admin。
- 删除组织不属于“保留至少一名 admin”的例外业务操作，因为组织本身及其成员关系将整体删除。

实现时先锁定 Organization 行，再锁定/检查相关 Membership，避免两个 admin 同时降级或移除导致零 admin。仅依赖请求开始时的计数检查不合格。

## 6. 组织上下文与切换

- 当前组织 ID 可出现在 `/orgs/:orgId/*` 路由和客户端 OrganizationContext。
- 客户端保存的“最近组织”仅是显示偏好，可使用非敏感本地存储；不是授权证明。
- 每次组织 API 请求都以认证用户 ID + 路由 organizationId 重新检查有效 Membership。
- 切换组织只改变后续导航和查询上下文，不修改全局用户角色。
- 当前组织被删除或用户被移除后，清除失效偏好，跳转组织列表、其他有效组织或创建组织页。
- 刷新页面后先恢复 Auth 用户，再查询组织列表和当前组织权限；不得因本地缓存直接展示受保护数据。

## 7. 默认路由决策

| 场景                              | 默认去向                         |
| --------------------------------- | -------------------------------- |
| 注册/登录后存在有效邀请恢复上下文 | 邀请校验与接受流程               |
| 无邀请且用户没有组织              | 创建组织页                       |
| 无邀请且最近组织仍是有效成员      | 最近组织 Dashboard               |
| 最近组织失效但有其他组织          | 按稳定顺序选择其他有效组织并提示 |
| 接受邀请成功                      | 被邀请组织 Dashboard             |

路由决策不能只看“是否已登录”，必须同时考虑邀请上下文和实际 Membership。

## 8. 项目归属与权限叠加

1. 未来 Project 表必须包含非空 `organizationId`，不存在仅属于个人或无组织的项目。
2. Membership 是访问组织项目的必要条件，不是充分条件。
3. 项目授权必须依次检查：有效组织 Membership → 项目属于该组织 → 项目级权限允许操作。
4. org admin 是否默认拥有全部项目权限属于项目模块决策，本 PRD 不隐式授予；不得用组织 member 身份绕过项目限制。
5. 当前没有 Project 表或历史个人项目，因此无需编造数据迁移；项目首次落地时必须同步满足本约束。
